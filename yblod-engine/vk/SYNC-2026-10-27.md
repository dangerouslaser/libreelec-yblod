# dv-engine-vk: what changed in the LibreELEC port (2026-10-27)

For the agent working on AMD support in the engine. This lists every engine change made while porting
big-fella's `dv-engine-vk` into LibreELEC (Kodi). It covers what each change does, where it is,
what was measured, and what to watch for on AMD. Please send your AMD changes back the same way
(see "Syncing back").

### What is Kodi-specific, and what changes mpv

Kodi motivated these changes, but most are general. Synced into big-fella, **two change mpv's behaviour by default**:
- **The fused GUI overlay** (change 4). It applies whenever the overlay is the shell's OSD layer alone, i.e.
  no subtitles on screen. So mpv/KWin frames without subtitles take it. It has only been verified exact
  through Kodi. Run `DVVK_VERIFY=2` with mpv; `DVVK_OVERLAY_PREPARE=1` reverts to the old pass.
- **The implicit read fence on the overlay buffer** (change 3). It is now also attached to KWin's forwarded OSD
  dmabuf, so KWin's next draw into that buffer waits for the engine's read on the GPU. That is correct, but
  new: before, mpv relied only on `dvvk_overlay_ticket` to hand buffers back.

These help mpv too, with no behaviour change: the leak fix (change 1; a real bug there too) and the
`DVVK_PROFILE` async path (change 2). These are opt-in: `DVVK_VERIFY`, fused Annex B and the changed-pixel count.
`DVVK_OVERLAY_FLIP_Y` only matters for a GL framebuffer (Kodi). Everything in the Kodi patch is Kodi-only:
- the async adapter;
- no per-frame `glFinish`;
- the shared GUI framebuffer;
- the revision check;
- the nearest-EL setting.

The shaderc and Mesa packaging is LibreELEC-only.

## Engine changes, by commit

All engine paths below are relative to `/Users/bryanhoban/Projects/libreelec-yblod-engine-integration/yblod-engine/vk/`.

### 1. Leak fix: output fd dups never closed (cb8e8d503f) — **upstream has this bug**
`src/engine.rs`, `impl Drop for Engine`. It `drain(..)`ed `self.outputs` to destroy the imports, then
looped over the now-empty `self.outputs` to close the fds. So the two output dmabuf dups, and the
scanout buffers they pin, were never freed. Kodi creates an engine per video: about 140 MB a video,
until the kernel's OOM killer took Kodi. mpv keeps one engine per session, so it barely shows there,
but it is the same bug. The fix closes the fd in the drain loop.

### 2. DVVK_PROFILE on the asynchronous path (0fdd034c05)
`src/engine.rs`: `Ctx.query`, `Profile`, `collect_frame`/`collect_profile`, and `stamp()` in `record_submit`.
Before this, the profile only ran in `render()` (the synchronous harness). Now each ring context has its own
4-point timestamp pool: start, after reconstruction, after overlay prepare, after pack. It is read back when
the context is reused, which `submit` already waits for, so there are no extra waits. Every 120 frames it prints, on stderr:
`dvvk profile: gpu X ms (p95, max) = reconstruction + overlay prepare (n of 120 frames) + pack; plan ms CPU`.

### 3. GUI read in place: `dvvk_set_overlay_ex` + read fences (31e770aa91)
- `src/capi.rs`, `include/dv_engine_vk.h`:
  - `dvvk_set_overlay_ex(e, buf, id, flags)` with `DVVK_OVERLAY_FLIP_Y` (rows bottom first, i.e. a GL framebuffer's texture).
  - `dvvk_implicit_failed(e)`.
- `src/overlay.rs`: `Sources.shell_flip`.
- `shaders/overlay_prepare.comp`: the `flip` push constant.
- `src/engine.rs`: after `queue_submit2`, the frame's sync_file is imported into the shell dmabuf as an
  **implicit read fence** (`DMA_BUF_SYNC_READ`), as well as into the output (write fence). So the
  overlay's writer, here Kodi's GL, can draw the next GUI into the **same** buffer immediately: its GPU
  write waits for the engine's read. There is no copy and no CPU wait. If the import fails (older kernel),
  `implicit_failed` is set and the caller must wait for the ticket.
- Also in this commit: `Sources.consumed` (overlay id → ticket) is capped at 1024 ids. Kodi uses a new id every frame and never calls `dvvk_overlay_ticket`.
- Kodi side: the GUI framebuffer's texture is given a GBM buffer as storage
  (`glEGLImageTargetTexture2DOES`). It uses the driver's single-plane modifier, else linear; on Intel it got Y-tiled, `0x100000000000002`.

### 4. GUI overlay fused into the pack (ac8e1fd838, refined in aafde1867f)
`shaders/pack.comp` has a new `OVERLAY == 2` specialization. `src/engine.rs` has `fused_overlay()`, an `overlay_kind`
of 0/1/2 (now 27 pack pipelines), new pack bindings 15–17 (shell sampler, keys, coefficients) and `PackPush.gui_flags`.
- It is used when the overlay is the shell's layer alone (no subtitle atlas). The pack reads the shell itself, so there is no
  `overlay_prepare` pass and no tile map. For mpv with subtitles, the prepare pass runs as before.
- **Cache**: a pixel's colour is cached against its RGBA key, and recomputed only when the key changes.
  - Each pixel's entry (colour + key) is written only by the invocation that **owns** it.
  - Each workgroup (32×2 invocations = 128×4 pixels) resolves its pixels into `shared vec4 gui_shared[4][128]` (8 KB), then hits a barrier.
  - The chroma blend's left neighbour comes from shared memory. At the workgroup's left edge it is computed directly (`gui_foreign`), not read from a cache entry another workgroup may be writing.
- Transparent pixels read no key (aafde1867f). Their colour is zero, and a stale key still names its own colour.
- An invalidation (new coefficients, or a mode switch) rewrites every key, as `overlay_prepare` does.
- Colour errors are stored as `w = -1` and re-reported on every frame that hits them.
- `DVVK_OVERLAY_PREPARE=1` keeps the old pass.

### 5. DVVK_VERIFY (ac8e1fd838, in place since 04544b723d)
- `shaders/verify_compare.comp` is new.
- `src/engine.rs`: `Verify`, `record_reference`, and `record_staged`. `record_staged` is the staged reconstruction, factored out of `record_submit`.
- `DVVK_VERIFY=k`: every k-th frame is rendered **again** into a scratch output by the reference route:
  - the staged reconstruction;
  - `overlay_prepare` with invalidate, which rebuilds the real colour cache in place (fresh entries are what any cache must hold);
  - the source-0 pack.
  
  The shown output is then compared with the scratch output word by word on the GPU. Any difference is printed with the frame and the first pixel, and there is a summary every 120 checked frames.
- Extra memory is about 35 MB. A private-cache version needed about 200 MB and ran the VM out of device memory.
- This is the correctness gate for any fused or AMD-specific route: **0 differences is the bar**.

### 6. Annex B on the fused route, shared vertical taps (d777cdef59) — **opt-in, slower here**
- `shaders/fel_chroma.comp`: `el_tile[39]`, `el_chroma_tiled`.
- `shaders/pack.comp`: `el_tile[4][71]`, `el_tiled` in `fel_luma`.
- `src/engine.rs`: the route choice and `annexb_fused`.

What it does: each workgroup computes the vertically upsampled EL once into shared memory (pass A: 32 EL chroma columns plus the 8-tap halo; the sited pack: 64 EL luma columns plus the halo, × 4 rows). The horizontal 8-tap filter then reads the tile. The arithmetic is unchanged.

It is opt-in with `DVVK_ANNEXB_FUSED=1`, and staged stays the default. It is exact (verify: 840/840 frames), but at a fixed 1000 MHz on Intel it took 12.8 ms against 11.1 ms staged. The fused pack's per-pixel luma costs more than the staged kernels it replaces; even nearest-fused has a 5.9 ms pack against 2.3 ms staged.

### 7. Changed-pixel count (5f443b8e0f; diagnostic since aafde1867f)
- `dvvk_overlay_changes(e, ticket)` returns how many shell pixels changed since the previous frame, or -1 if unknown.
- With `DVVK_OVERLAY_CHANGES=1` the fused pack keeps keys for every pixel (transparent ones too) and counts the differences: a per-invocation count, then a workgroup `atomicAdd`, then one global atomic.
- Kodi uses it to check whether its GUI revision can be trusted for skipping the GUI. Result so far: 0 misses in about 4,800 frames. It is not trusted yet.

## New API and switches

| | Default | What |
|---|---|---|
| `dvvk_set_overlay_ex(e, buf, id, DVVK_OVERLAY_FLIP_Y)` | — | Overlay with flags. Each reading frame leaves an implicit read fence on the buffer. |
| `dvvk_implicit_failed(e)` | — | 1 if a fence couldn't be attached: wait for tickets instead. |
| `dvvk_overlay_changes(e, ticket)` | — | Changed overlay pixels (needs `DVVK_OVERLAY_CHANGES=1`). |
| `DVVK_PROFILE=1` | off | Per-stage GPU timing every 120 frames (stderr). |
| `DVVK_VERIFY=k` | off | Re-render every k-th frame by the reference route and compare. |
| `DVVK_OVERLAY_PREPARE=1` | off | Use the separate `overlay_prepare` pass instead of the fused one. |
| `DVVK_ANNEXB_FUSED=1` | off | Annex B FEL on the fused route. |
| `DVVK_OVERLAY_CHANGES=1` | off | Count changed overlay pixels. |

## Measurements (Tiger Lake i5 Iris Xe, ANV, Kodi, petunia VM)

How they were taken:
- **Pin the GPU clock.** In async mode the GPU drops its clock and GPU times inflate up to 2×. On i915: `echo 1000 > /sys/class/drm/card0/gt_max_freq_mhz; echo 1000 > .../gt_min_freq_mhz`, then restore 100/1300. On AMD the equivalent is `power_dpm_force_performance_level` (e.g. `profile_standard`).
- Each run is 75 s, with Kodi restarted before it.
- Clips: 1917 from 33:56 (profile 7 FEL, 24p) and Gemini Man from 0:00 (profile 7, single-layer route, 4K60).

Results at 1000 MHz, OSD held open:

| Gemini Man 4K60, OSD open | Kodi render thread | Skips (2 runs) | Engine GPU |
|---|---|---|---|
| Before (GUI copied every frame + prepare pass) | 66% | 7, 3 | 7.06 ms |
| GUI read in place (change 3) | 55% | 0, 0 | 7.22 ms |
| + fused overlay (change 4) | 54% | 0 | 7.21 ms |

| 1917 FEL, at 1000 MHz | GPU ms/frame |
|---|---|
| Annex B staged (default) | 11.1 (reconstruction 8.8 + pack 2.3) |
| Annex B fused (opt-in) | 12.8 (pass A 4.4 + pack 8.4) |
| Nearest fused | 10.1–10.4 (pass A 4.2 + pack 5.9) |
| OpenCL engine, for reference | about 4.5 reconstruction + 2.2 pack |

The fused overlay ties the prepare pass here and was kept as the default for bandwidth-bound GPUs (Pi 5).
The largest remaining gap is the staged FEL reconstruction: 8.8 ms on Vulkan against about 4.5 ms in OpenCL.

## Things that may differ on AMD

- **Fused paths are the A/B to run first.** `DVVK_OVERLAY_PREPARE=1` against the default, and `DVVK_ANNEXB_FUSED=1` against staged. Both were a wash or a loss on Intel's ALU/bandwidth balance; RADV's could differ. Use `DVVK_VERIFY=2` while testing.
- **Workgroup assumptions.** The pack is 32×2 invocations per workgroup, one workgroup = 128×4 pixels, with up to three `barrier()`s and about 9.2 KB of shared memory (`gui_shared` plus `el_tile`) when both features are on. On RADV wave64/wave32 this may want a different local size. The 128-pixel workgroup width is baked into the shared-array indexing (`lx * 4`, `[128]`, `[71]`). Change both together.
- **Implicit sync.** The read-fence import (`DMA_BUF_IOCTL_IMPORT_SYNC_FILE`) needs kernel 6.0 or later, which amdgpu supports. Check `dvvk_implicit_failed` stays 0.
- **GUI buffer layout.** Kodi asks GBM for a single-plane layout, else linear. AMD often returns DCC or multi-plane modifiers, which fall back to **linear**. The engine imports whatever modifier it is given (`dmabuf::import_image`), so a linear GUI on AMD is expected, not a bug.
- **RADV in LibreELEC.** Generic's Mesa build here is ANV-only (`packages/graphics/mesa/package.mk`, commit 238785ea95), because RADV's addrlib failed to link (`undefined reference to '__cpu_model'`). LibreELEC on AMD would need that fixed first. It doesn't affect big-fella's Arch builds.
- **Memory.** About 470 MB of the engine's device memory is allocated at create time. The mpv-only subtitle atlas, 6 × 24 MB host buffers, is allocated even in Kodi; lazy allocation is a possible saving on smaller GPUs.
