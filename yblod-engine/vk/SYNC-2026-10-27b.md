# dv-engine-vk: changes since SYNC-2026-10-27.md

A follow-up to `SYNC-2026-10-27.md`, for the agent working on AMD. big-fella already has that first set,
up to `8ffeaa9` (the LibreELEC branch's `aafde1867f`). This covers the 3 engine commits after it. They
come from investigating why Vulkan's staged FEL reconstruction is about 2× slower than the OpenCL engine on Intel.

**The bottom line on Intel:** nothing here changes the playback result. 4K60 with the OSD up already plays
with no skips or drops (Gemini Man), so further FEL work was parked. One small exact speed-up is now on by
default. One switch, `DVVK_SUBGROUP`, was made for **wave32/wave64 testing on AMD**.

## 1. DVVK_PROFILE breaks the staged FEL chain down by kernel (61e82e383f)

`src/engine.rs` changes:
- `PROFILE_FEL_POINTS` (7 timestamps per ring context instead of 4);
- `Ctx.fel_stamped`;
- `Engine.fel_query`;
- `stamp()` in `record_fel`;
- `Profile.fel`.

Frames on the staged FEL route (`record_fel`) get three more timestamps: after `vertical_pair`, after
`luma_phase_guide` and after `phase_vertical_uv`. With `DVVK_PROFILE=1`, every 120 frames a second line follows the usual one:

```
dvvk profile: staged FEL (120 frames): vertical_pair A + luma_phase_guide B + phase_vertical_uv C + chroma D ms
```

`chroma` is the dual MMR + horizontal pass, or the scale + table-add/MMR passes. The stamps are only read back
for frames that wrote them, so other routes' profiles are unaffected. The DVVK_VERIFY reference pass doesn't stamp.

## 2. vertical_pair with 32-bit stores — on by default, exact (83af92a74a)

- `shaders/fel_vertical_pair_w32.comp` (new): two adjacent EL columns per invocation, so each output row is
  **one dword store** instead of two 16-bit stores. Error bits are collected locally, with **one `atomicOr` per
  invocation** instead of one per sample. The arithmetic is identical; the output buffer is declared `uint[]`
  and holds pairs of 16-bit samples.
- `src/engine.rs`:
  - `FelPipelines.vertical_pair_w32`;
  - `Engine.w32` (`DVVK_W32=0` keeps the original);
  - `Engine.reference_pass`.
  
  The **DVVK_VERIFY reference always uses the original `fel_vertical_pair`**, so verify checks the new kernel against the old one word for word.
- Result on Intel at a fixed 1000 MHz: `vertical_pair` 1.55 → 1.22 ms (−21%); 840 frames, 0 differed.

## 3. DVVK_SUBGROUP: a required compute subgroup size (89ee69e954) — off by default

- `src/device.rs`: reads `PhysicalDeviceVulkan13Properties` (`min/max_subgroup_size`,
  `required_subgroup_size_stages`). With `DVVK_SUBGROUP=N`, it enables `subgroup_size_control` if N is a power of two
  within the range and compute is in the required-size stages. Otherwise it prints
  `dv-engine-vk: DVVK_SUBGROUP=N not supported (subgroup sizes a-b), the driver's choice`. The size is kept in `Device.subgroup_size`.
- `src/gpu.rs` (`Pipeline::new`): chains `PipelineShaderStageRequiredSubgroupSizeCreateInfo` onto **every** compute
  pipeline when it is set. It doesn't require full subgroups, so there is no constraint on local size beyond the device limits.
- **On Intel it is a loss, so leave it unset.** Mesa picks SIMD16 for every engine kernel. Forcing 32 helped only
  `luma_phase_guide` slightly (3.50 → 3.29 ms). It badly hurt the big shaders: the pack went from about 5 to 25.7 ms on Gemini Man, and
  dual MMR from 3.4 to 5.2 ms. Output stayed exact.
- **On AMD it is the wave32/wave64 switch.** RADV picks a wave size per shader. `DVVK_SUBGROUP=32` and `=64` give a
  one-environment-variable A/B with `DVVK_PROFILE=1`. If the best width differs per kernel (as it does on Intel), the
  next step is a per-pipeline size rather than this global one. That would mean a `subgroup` argument on `Pipeline::new`, set where each pipeline is created in `Engine::new`.

## What the investigation found (Intel; may or may not carry over to RADV)

Staged FEL on 1917 (Annex B) at a fixed 1000 MHz, per kernel. Vulkan ≈ 2× OpenCL throughout:

| Stage | Vulkan | OpenCL |
|---|---|---|
| EL vertical, luma + chroma | 1.55 + 0.23 ms | 0.65 ms |
| `luma_phase_guide` | 3.5 ms | 1.8–2.2 ms |
| Chroma dual MMR + horizontal | 3.4 ms | 1.6–1.8 ms |

Compiler output compared: Mesa via `INTEL_DEBUG=cs` + `MESA_SHADER_CACHE_DISABLE=true`; IGC via `IGC_ShaderDumpEnable=1` + `NEO_CACHE_PERSISTENT=0`.
- **No register spills** in any engine kernel.
- **Every `uint16_t` SSBO access becomes `byte_scattered_read/write:d16`** in Mesa's Intel backend. IGC also byte-scatters
  16-bit stores, but the planes and lookup tables are 16-bit everywhere in the engine, so this costs all over. On
  RADV, 16-bit buffer access compiles differently (`buffer_load_ushort` etc.), so check before porting the fix. Fix pattern:
  - pack pairs into dwords for stores, as in change 2;
  - read tables and planes as `uint[]` with a shift.
- **The per-sample error `atomicOr`** (`ERROR_OR` in each shader, from `input_sample`/`input_uv` in
  `shaders/common/dv_common.glsl`) is a full 16-lane atomic in Mesa after every texel read. IGC emits one single-lane
  atomic per thread, predicated on any lane. Fix pattern: local accumulation, one atomic at the end, as in change 2. On AMD
  it may be worth checking the RADV ISA (`RADV_DEBUG=shaders`) for the same.
- Not yet compared kernel by kernel: `luma_phase_guide` and dual MMR, which have 16-bit table gathers and 64-bit math. That is
  where the rest of the 2× is. **Parked**: Intel already has the headroom it needs.

## Switches added in this round

| | Default | What |
|---|---|---|
| `DVVK_W32=0` | on (1) | Use the original `fel_vertical_pair` (16-bit stores) instead of the 32-bit one. |
| `DVVK_SUBGROUP=N` | unset | Required compute subgroup size for all pipelines (AMD: 32/64; Intel: leave unset). |
| `DVVK_PROFILE=1` | off | Now also prints the staged FEL per-kernel line. |
