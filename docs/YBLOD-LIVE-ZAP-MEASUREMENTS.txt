Method
tools/yblod/measure-live-zap.py sends Player.Open over TCP JSON-RPC and records
notification arrival using the client's monotonic clock. A debug-log slice
records demux, codec, renderer, display and synchronization milestones. Log
times use the device clock and are relative to the first selected log event;
use the input_open event to normalize comparisons. API replies are not the
onset of playback, and Player.OnAVStart is not a physical first-visible-frame
measurement. In channel-to-channel runs the final HDMI commit often follows
OnAVStart. Hardware/TV acceptance and visible pixels were not instrumented.

Two initial captures used debug logging only. Five subsequent captures also
used tools/yblod/live-zap-trace.c as a temporary LD_PRELOAD probe, compiled
against the matching LibreELEC SDK. It forwards all calls unchanged and times
avformat_open_input, avformat_find_stream_info, close and initial packets.
Artwork also opens through FFmpeg: distinguish format=jpeg_pipe/png_pipe
from the format=mpegts video opens. Probe times are device CLOCK_MONOTONIC;
do not subtract them directly from local notification times or wall-clock logs.
Instrumentation may add overhead; these are short controlled samples, not
population percentiles. No stream URLs or payloads appear in recorded JSON.

Confirmed bottleneck
All five traced channel starts successfully opened MPEG-TS twice, with a close
between the two opens:
Sample                    First open   Second open   Combined
Menu -> Sky                 1.519        1.505          3.024
Sky -> WCVB #1              1.461        1.439          2.900
WCVB -> Sky #1              1.570        1.508          3.078
Sky -> WCVB #2              1.842        1.422          3.264
WCVB -> Sky #2              1.455        1.610          3.065
No separate avformat_find_stream_info call was observed in these live runs.
Open-call timings include network/server response, initial reads, format
recognition and demux header work; they do not independently measure each.
The current evidence cannot attribute the ~1.5 s of a single open specifically
to provider latency versus format/header acquisition.

Code correlation
Prepared Kodi DVDStreamInfo path starts with unknown FPS for Sky; the tested
decoder-rate fix now supplies it before renderer configuration.
In CDVDDemuxFFmpeg::Open, the FFMPEG-input result<0 branch successfully calls
avformat_open_input, then immediately closes it, allocates a new context and
opens again with load_all_variants=0. The block is not restricted to HLS.
This matches the measured pair of successful MPEG-TS opens. It is separate
from the later transport-stream full-analysis reopen logic.
FFmpeg's original load_all_variants proposal is specifically an HLS option:
https://ffmpeg.org/pipermail/ffmpeg-devel/2017-December/221605.html

Ranked next experiments (not implemented by this measurement task)
1. For realtime MPEG-TS, retain the first successfully opened format context
   rather than reconnecting. Preserve HLS variant-selection behavior and all
   failure cleanup. Estimated opportunity: one 1.42..1.61 s open per switch;
   this is NOT a measured speedup. Validate both channels repeatedly, audio,
   HEVC headers, late joins, reconnects and movie/HLS paths before broadening.
2. Coordinate initial HDR and refresh-rate output changes. The representative
   Sky run first sets HLG at 60 Hz and then changes to 50 Hz. WCVB/Sky switch
   notifications can claim AV start before the final HDMI commit. This is a
   separate startup-ordering opportunity, not justification for disabling rate
   matching. Renderer-to-final-commit spans roughly 0.5..0.9 s in these runs.
3. After (1), separately measure the remaining single-open network/header wait
   before touching probe sizes or keyframe/buffer policy. Avoid unconditionally
   shortening probes: correct codec headers, audio and frame rate are required.
