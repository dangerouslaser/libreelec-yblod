# Native integer arithmetic foundation

`native_composer.c` and `native_composer.h` implement the standalone mapper,
enhancement correction and final composition contracts in C. They do not call
the Python reference, Kodi or libplacebo. This is a reusable scalar foundation,
not a playback backend, decoder, RPU parser or licensed-player implementation.
No fractional scaler-input policy or production default is selected. Python is
the independent test oracle; the arithmetic implementation is native C.

## Supported contracts

- Base mapping: native 8/10-bit integer Y/Cb/Cr triplets, denominator 13..32,
  three component mappings, 2..17 strictly increasing pivots per component,
  linear/quadratic polynomial segments and chroma-only MMR orders 1..3.
- MMR callers supply an explicitly prepared luma guide in the triplet. Each
  channel is bounded by its own pivot endpoints. Intermediate product floors
  are retained; the internal pivot belongs to the interval on its right.
- Enhancement correction: native 8/10-bit integer codes, denominator from
  input depth plus five through 32, metadata accumulator bound before signed
  flooring, and exactly zero correction at the neutral code.
- Composition: mapped base 0..65535 plus signed 64-bit correction, addition
  before one 10/12-bit output round, half ties toward positive infinity, then
  final output clipping. Base-only composition supplies an explicit zero
  correction; invalid/missing enhancement input never implies fallback.

Coefficient ranges match the Python stage envelope, not a complete Dolby
bitstream legality check. A frame adapter must also apply the global metadata,
dimensions, frame-identity and enhancement-depth denominator constraints.
No decoding, chroma expansion, EL scaling, colour conversion, HDMI metadata,
display adaptation or buffer ownership is supplied by this API.

## C representation and safety

The header uses fixed-size caller-owned structures. Initialize them to zero,
then populate only the declared active pivots/segments/coefficients. Unused
fields must stay zero; polynomial segments have no separate constant field.
Every scalar call revalidates metadata. Do not mutate it concurrently.
Outputs remain unchanged on a nonzero status. Null pointers, invalid field
ranges, out-of-depth codes and unsupported methods are rejected.

C scalar types do not preserve a JSON value's original type. A JSON/FFI adapter
must reject booleans, floats and values outside the C type before conversion;
this library validates the integer values it receives, not their provenance.
The ctypes conversion helper in the tests is a fixture adapter, not that parser.

GCC or Clang with signed `__int128` support is required. The mapper's accepted
MMR coefficient envelope exceeds 64-bit intermediate accumulation at its
largest denominator. The fixed maximum metadata size and bounded terms fit
comfortably inside signed 128 bits. The implementation floors signed values
using division and remainder, never an implementation-defined negative right
shift. Wide composition addition also avoids overflow at either signed 64-bit
correction endpoint. No extra residual-storage clamp is imposed.

The C API intentionally accepts finite signed 64-bit explicit corrections,
unlike Python's arbitrary-size `compose_residual` argument. All corrections
generated by the validated NLQ envelope fit this representation. The standalone
dump adapter remains responsible for checking its separate signed-32-bit file
storage range; no dump-format decision is made here.

`yb_process_chunk` accepts 1..65536 same-count integer samples and processes
one component using an explicit Y/Cb/Cr triplet per position. All three input
arrays are required; chroma's Y array is its prepared luma guide. Unused luma
Cb/Cr may be zero arrays. Enhancement-enabled chunks require their own NLQ
configuration and EL array, with the same global denominator as the mapper.
Disabled chunks require both enhancement arguments to be NULL, rather than
silently ignoring an extra layer.

Metadata and every input code are validated before the first output write.
The four outputs are mapped base, signed correction, unrounded signed sum,
and reconstructed output. Chunk correction/sum arrays are signed 32-bit: the
validated coefficient bound keeps correction magnitude below 2^17 and sum
below 2^18, without introducing a new clamp. Inputs and metadata must stay
stable during the call. Output buffers must not overlap one another, inputs
or metadata. Alignment and pointer-range overflow are checked; allocation
lengths and pointer validity remain the C caller's responsibility.

Metadata is bounded and processing uses constant working memory. Chunk calls
validate once and use fixed-point native arithmetic for every pixel, avoiding
one FFI call per sample. ABI version and structure-size queries allow adapters
to reject incompatible libraries. No CPU throughput or real-time playback
claim has been measured.

## Verification

```sh
python3 -m unittest test_native_composer
cc -std=c11 -O2 -fPIC -shared -Wall -Wextra -Werror \
  -Wconversion -Wshadow native_composer.c -o libnative_composer.so
```

The tests compile into a temporary directory and compare against the unchanged
reference: 69,120 polynomial cases, 23,040 MMR cases, 107,520 correction cases,
and 215,040 final-composition comparisons (both output depths for every
correction case). Fixed literal checks include
MMR intermediate truncations, separate channel pivot clamps, interval ownership,
binding limits, signed floors, output half ties, and signed-64-bit endpoints.
Invalid inputs/configurations and unchanged outputs on failure are tested.
Chunk tests additionally compare all four stages across mixed input depths,
all MMR orders and output depths, cover the maximum chunk size, and check late
invalid samples, disabled layers, aliases, alignment and address-range overflow.

Initial local verification used Apple Clang 17 on arm64 with the flags above.
Compiler/version and target-specific build verification must accompany further
deployment. The tests verify arithmetic, not GPU execution, licensed Dolby
conformance, real-film accuracy or a match to the SK4.

Next add a bounded prepared-frame adapter and differential every-stage output
tests before exposing any experimental playback integration. Existing HDMI
packing and presentation ownership can stay separate from these arithmetic
stages; hardware scaling remains an upstream contract decision.
